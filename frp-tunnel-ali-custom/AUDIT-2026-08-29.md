# Audit — FRP Tunnel Ali Custom v1 → v2

**Audit date:** 2026-08-29  
**Audited branch:** `agent/frp-tunnel-ali-custom-v1`  
**v1 head at audit:** `462b6b5268014754245cedc594d84e2fd6dc70bb`

## What v1 got right

- `transport.tcpMux = false` is the correct stability baseline for this project.
- With FRP v0.71.0, disabling TCP mux means `Connect()` opens a real transport connection instead of a yamux logical stream.
- WSS/TLS keeps FRP control/work payloads out of plaintext.
- Compression is disabled for already-compressed/encrypted VPN/video traffic.
- Xray/3x-ui is intentionally outside the installer.
- FRP release archives are pinned to v0.71.0 and SHA-256 verified.

## Blocking findings fixed in v2

1. **TLS identity was not verified.**  
   v1 did not configure `frps` with a real certificate and did not configure `frpc` with `trustedCaFile`. FRP therefore generated a self-signed server certificate and the client TLS configuration used `InsecureSkipVerify` when no CA file was supplied.

2. **Moving source URL.**  
   The documented installer URL used the moving branch. v2 production bootstrap is pinned to an immutable commit.

3. **Health false positives.**  
   v1 Iran health did not fail on a missing public listener, and Foreign health did not require proxy state. It also lacked an end-to-end public-port test.

4. **Generic FRP binary paths.**  
   v1 wrote `/usr/local/bin/frps` and `/usr/local/bin/frpc`, potentially colliding with another FRP installation. v2 uses `/opt/frp-tunnel-ali/bin`.

5. **No rollback/diagnostics gate.**  
   v2 adds config backups, validated rollback, TLS status, read-only diagnostics, and a final readiness gate.

6. **Token embedded in TOML.**  
   v2 stores the token in a mode-0600 file and uses FRP tokenSource plus authentication scopes for HeartBeats/NewWorkConns.

7. **No automated project-specific checks.**  
   v2 adds shell/static checks and FRP config-schema smoke tests in GitHub Actions.

## Residual limitations

- FRP WSS uses the upstream fixed WebSocket path `/~!frp`. It is inside TLS, so passive DPI cannot read that path, but a successful active TLS probe can still fingerprint the endpoint.
- Go TLS has its own ClientHello fingerprint and is not browser impersonation.
- No TCP-based tunnel can guarantee zero stalls under packet loss; v2 isolates unrelated user streams so one lossy work connection does not share congestion control with other work connections.
- This release candidate is **not production-proven until it survives real traffic**.
- Shared Maya1/Maya3 spare selection, Cloudflare failover and Telegram orchestration remain a later layer after core tunnel validation.
